One Windows sign-in through the KVM

Use the separately encrypted KVM and Windows credentials without exposing their values to the model. The operator has authorized a sign-in attempt and approved the exact KVM certificate pin.

Implementation

  1. Add pinned binary snapshot support and a bounded local console session. A fresh T3 private key submission decrypts both credentials for this single operation.
  2. Keep secrets and the KVM token only in the helper process. The operator/agent receives local console images and sanitized command results.
  3. Inspect the Windows screen before acting. Limit controls to snapshots, sign-in navigation, fixed stored username entry, and one stored-password submission into a visually verified field.
  4. Require a recent snapshot reference and confirmed field coordinates before secret entry. Stop on ambiguous focus, account errors, changed pins, or failed login; never retry the password automatically.
  5. Inspect the resulting screen, then log out of the KVM and terminate the helper. Do not change Windows settings, run commands, or control power.

Console screenshots can contain private desktop information and stay under ignored .local/. This trusted helper workflow is not isolation from unrestricted same-account processes. Visual verification is required; the helper cannot prove the semantics of an arbitrary native password field.

Live outcome

Windows accepted one Administrator password submission on 27 October 2026. A post-submit screenshot showed the Windows Server desktop. The KVM session was logged out and the helper terminated; Windows remains signed in. No password or session token entered tool output, and the submitted private key copy was consumed.

Validation

Test credential binding, navigation limits, snapshot freshness, one-attempt enforcement, TLS pinning, and cleanup before collecting a fresh private key. A successful API password submission alone is not proof that Windows accepted it; inspect the post-submit console.
